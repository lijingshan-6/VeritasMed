# Flash 网关观测：返回标识与用量

2026-09-24。只记录可观察到的 API 行为，不验证底层模型权重或提供方身份。

## 已确认的事实

首轮 30 条 SciFact 试跑使用统一请求配置；保存的响应模型字段中，29 条为
`deepseek-v4.1-flash`，1 条为 `deepseek-v4-flash-0731`。只有后者保存了 usage。
历史响应的完整原始流没有保存，不能事后还原是哪一层产生这些差异。

本轮对首轮已经暴露的一条 claim 发起 6 次相同请求，直接读取 OpenAI-compatible SDK
的原始流式 chunk。保持 Flash 请求 ID、high reasoning、JSON 输出和 token 上限一致，
最多同时 3 次。未让模型自报身份，未保存隐藏推理内容，只记录字符数与元数据。

结果：6 次均正常完成；各请求的全部 chunk 仅出现 `deepseek-v4.1-flash`，6 次都有 usage。
记录见 [原始流元数据](../data/verification/gateway_probe/run01/probe.json)。
这说明**当前这 6 次请求的返回标识一致**，不能证明历史差异已修复，也不能证明固定权重。

本地 LangChain 适配器的单个 `response_model` 字段不足以呈现全部 chunk 的标识。
新研究运行改用独立 `FlashGateway` 直接收集流中所有不同模型名及 usage 快照；
仍通过原有 `.env` 中的 Flash 配置调用同一端点，不变更 v0.4 问答路径。
这是一项观测能力改进。当前没有证据足以认定 LangChain 是历史缺失用量的根因。

## 研究约束

- 不把请求 ID、`/models` 列表或模型自述当作底层权重证明。
- 一次请求若出现多个标识，全部保留；不覆盖成最后一个名称。
- 缺失 usage 保持未知；流中多次累计 usage 以最后快照作该逻辑请求汇总，不相加重复计费。
- SDK 传输重试中已消耗但未返回的用量未必可见，API 报告总量不等于账单核对。
- 新比较在时间上交错三种方案并记录元数据；观测标识一致仍不足以完全消除网关路由混杂。
- 若再次出现不同标识，主结果仍保留全量，不能按事后筛选出的“干净子集”宣称某方案胜出。

底层路由规则需要服务提供方说明，当前保持“原因未确认”。项目可以继续开发诊断与报告，
但严谨的单模型机制归因必须注明这个限制。
